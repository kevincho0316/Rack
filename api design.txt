Here's a clean REST design for Rack. I'll cover your 4 commands and suggest the missing pieces you'll need for file sync to actually work.

## Core entities

- **Project** — a repository
- **Plate** — a commit; has `name`, `flag` (`Normal` | `Knot`), `note`, and a tree of files
- **Blob** — file content, addressed by hash
- **Tree** — mapping of file paths to blob hashes for a given plate

## Your 4 commands

```http
# 1. Download a blob by hash
GET /projects/{project}/blobs/{hash}
→ 200 (binary stream) | 404

# 2. Upload a blob (server returns the hash)
POST /projects/{project}/blobs
Content-Type: application/octet-stream
Body: <raw bytes>
→ 201 { "hash": "sha256:abc123..." }

# 3. Create a new project
POST /projects
Body: { "name": "my-project", "description": "..." }
→ 201 { "id": "...", "name": "my-project", "created_at": "..." }

# 4. Update flag/note of the latest plate
PATCH /projects/{project}/plates/latest
Body: { "flag": "Knot", "note": "stable release" }
→ 200 { ...updated plate... }
```

## What you're missing (and will need)

**Creating a plate.** Uploading blobs alone doesn't form a commit — you need something that groups blob hashes with file paths into a plate. Otherwise there's no "version" to sync to.

```http
POST /projects/{project}/plates
Body: {
  "name": "added login feature",
  "flag": "Normal",
  "note": "optional",
  "parent": "<previous plate id or null>",
  "tree": {
    "src/main.py":   "sha256:abc...",
    "src/utils.py":  "sha256:def...",
    "README.md":     "sha256:ghi..."
  }
}
→ 201 { "id": "plate_xyz", ... }
```

**Check if a blob exists before uploading.** This is huge for sync — clients shouldn't re-upload files the server already has.

```http
HEAD /projects/{project}/blobs/{hash}
→ 200 (exists) | 404 (need to upload)
```

You can extend this to a batch check, which is much faster when syncing many files:

```http
POST /projects/{project}/blobs/check
Body: { "hashes": ["sha256:abc...", "sha256:def...", ...] }
→ 200 { "missing": ["sha256:def..."] }
```

**Read history and individual plates.**

```http
GET /projects/{project}/plates              # list, paginated
GET /projects/{project}/plates?flag=Knot    # filter by flag (useful!)
GET /projects/{project}/plates/{plate_id}   # specific plate
GET /projects/{project}/plates/latest       # latest plate
```

**Get the file tree at a plate.** Clients need this to know what files exist and which to download.

```http
GET /projects/{project}/plates/{plate_id}/tree
→ 200 { "src/main.py": "sha256:abc...", ... }
```

**Diff between two plates.** Critical for efficient sync — only pull what changed.

```http
GET /projects/{project}/diff?from={plate_a}&to={plate_b}
→ 200 {
  "added":    { "src/new.py": "sha256:..." },
  "modified": { "src/main.py": "sha256:..." },
  "removed":  ["src/old.py"]
}
```

**Project listing/info.**

```http
GET /projects                  # list all projects
GET /projects/{project}        # project metadata + latest plate
DELETE /projects/{project}     # if you want delete
```

## Typical sync flow with this API

A client pulling latest would:
1. `GET /projects/{p}/plates/latest` → get latest plate id and tree
2. `GET /projects/{p}/diff?from={local_plate}&to={latest_plate}` → see what changed
3. `GET /projects/{p}/blobs/{hash}` for each new/modified file

A client pushing changes would:
1. Compute hashes of changed files locally
2. `POST /projects/{p}/blobs/check` → find which are missing on server
3. `POST /projects/{p}/blobs` for each missing blob
4. `POST /projects/{p}/plates` with the full tree

## Two design questions to think about

**Plate IDs.** Are they sequential (`plate_1`, `plate_2`) or content-hashed (like git's commit hashes)? Hashed gives you integrity and makes plates immutable + globally unique, but sequential is simpler. Since you're sync-focused, hashed is probably worth it.

**The `Knot` flag.** What does it mean semantically? If it's "locked / don't garbage collect / pinned checkpoint," your API might want a `GET /projects/{p}/plates?flag=Knot` endpoint and a rule that prevents deleting Knot plates. Worth deciding now since it affects storage logic.
